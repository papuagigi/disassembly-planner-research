- 대상 CAD: 05902(11개 제거), 06146(14개 제거).
  - v7.1 pilot에서 쓰인 CAD이지만, S4b 작성에는 쓰지 않았습니다(`mine.py`가 입력을 차단).
  - v7.2 planner는 이 CAD에 대한 기억이 없습니다.
  - 다만 v7.2 엔진 수정(H1 마감 처리, H3 메모리 한도)은 v7.1 pilot 때 이 CAD들에서 본 인프라 실패에서 나왔습니다.
- 공통 조건: gpt-6-luna/low. 에피소드마다 호출 8, 검사 240, 900초, 8 GiB. 물리 P2. 한 번에 1개씩 실행.
- 1차 시도: A(문서 없음), B(S3), C(S3) 각 1회.
  - 탐색 분기로 B(S4b), C(S4b)도 각 1회.
- 노트 작성: 같은 평가 모델(gpt-6-luna/low)이 1차 시도 기록 3개만 보고 조립체 전용 SKILL.md 노트 1개를 씁니다.
  - S3 분기는 A, B(S3), C(S3) 기록으로 씁니다.
  - S4b 분기는 A, B(S4b), C(S4b) 기록으로 씁니다.
  - 노트에는 성공한 제거 순서, 막힌 부품, 실제 방향 벡터, 낭비 지점이 들어갑니다.
- 2차 시도:
  - B(S3+노트)×2, C(S3+노트)×2.
  - 대조군: B(S3)×1, C(S3)×1, A×1.
  - 탐색 분기: B(S4b+노트)×1, C(S4b+노트)×1.
- A는 정의상 외부 문서를 쓰지 않는 조건이라 2차 시도에서도 노트가 없습니다. 이 비교는 "같은 조립체 경험을 기억해 쓰는 구조(B·C)"와 "기억 없이 다시 푸는 구조(A)"의 비교입니다.

## 핵심 결과

### 1) 같은 조립체 2차 시도: 노트를 쓴 B·C가 가장 빠르고 정확함

| 2차 시도 조건 | 성공 | 검사 수 (성공 에피소드) | 시간(s) |
|---|---|---|---|
| A, 기억 없음 (대조군) | 2/2 | 101 (05902), 48 (06146) | 754, 78 |
| B(S3), 노트 없음 | 2/2 | 108, 40 | 792, 104 |
| C(S3), 노트 없음 | 1/2 | 42 (06146) — 05902는 provider 오류 | 157 |
| **B(S3+노트)** | **4/4** | **11, 11, 14, 14** | 155, 129, 85, 71 |
| **C(S3+노트)** | **3/4** | **11, 11, 14** — 06146 1회는 계약 위반으로 0회 종료 | 126, 128, 68 |
| B(S4b+노트) [탐색] | 1/2 | 27 (06146) — 05902는 노트 미사용으로 실패 | 88 |
| C(S4b+노트) [탐색] | 2/2 | 11, 14 | 133, 69 |

- 노트를 쓴 2차 시도는 12회 중 10회 성공했습니다.
  - 성공 10회 중 9회는 **검사 수 = 필요한 제거 수(11 또는 14)**, 즉 실패 검사가 0회였습니다.
  - 기억 없는 A는 같은 CAD에서 48~101회 검사, 78~754초가 들었습니다.
- 05902에서는 1차 시도 때 B·C가 모두 900초 안에 끝내지 못했습니다(B 3/11, C 10/11). 노트를 쓴 2차 시도에서는 11회 검사, 약 130초에 끝났습니다.
- 노트를 쓴 2차 시도의 실패 2건은 모두 노트 내용 문제가 아니라 실행상의 문제였습니다.
  - **06146 C(S3+노트) 1회차:** 순위 응답에서 읽은 문서 3개 중 노트만 "적용"으로 표시했습니다. 상속된 v6 계약 규칙이 이를 즉시 종료로 처리했습니다(검사 0회, 9초). 이 규칙은 문서가 있는 B·C에만 걸립니다.
  - **05902 B(S4b+노트):** 모델은 노트를 적용했다고 선언했지만, 생성 코드는 노트의 순서를 쓰지 않고 S4b 일반 문서의 코드 틀(방향 계열 순위 루프)을 그대로 썼습니다(116회, 3/11, 시간 초과). 같은 노트로 C(S4b+노트)는 11회로 성공했습니다. C는 노트 순서가 순위로 들어가 호스트 DFS가 그대로 실행합니다.

### 2) 1차 시도 (처음 보는 조립체): CAD마다 결과가 반대

| 1차 시도 | 05902 | 06146 |
|---|---|---|
| A (문서 없음) | **성공 81회**, 684 s | 성공 225회, 637 s |
| B (S3) | 실패 3/11 (시간) | 성공 **53회**, 121 s |
| C (S3) | 실패 10/11 (시간) | 성공 83회, 435 s |
| B (S4b) [탐색] | 실패 3/11 (시간) | 성공 **38회**, 95 s |
| C (S4b) [탐색] | 실패 5/11 (시간) | 성공 54회, 173 s |

- **06146:** 문서를 쓴 B·C 네 조건이 모두 성공했고, A보다 검사를 2.7~5.9배 적게 썼습니다.
- **05902:** A만 성공했습니다.
  - 이 CAD는 성공한 제거가 전부 옆 방향(world ±y)이고, 위·아래는 한 번도 성공하지 못했습니다.
  - 검사가 느립니다(거절 2~3초, 불안정 판정 20~36초). 그래서 900초 안에 100회 남짓밖에 검사하지 못합니다.
  - 일반 문서가 탐색을 이 CAD에 맞지 않는 방향으로 끌었습니다.
    - S3: "같은 부품의 다른 방향 재시도" → B가 여섯 방향을 고르게 시도.
    - S4b: "위 > 옆 > 아래"를 라벨 이름으로 적용 → C(S4b)가 실제 아래 방향인 `+y` 라벨을 25회 시도.
  - 그 결과 시간 안에 끝내지 못했습니다(상세 분석은 STATUS 기록 참조).
- A의 결과도 크게 흔들립니다. 06146에서 1차 225회, 2차 48회로 같은 조건인데 4.7배 차이가 났습니다. 조건당 1회 결과로 순위를 단정하기 어렵습니다.

## 프로젝트 목표 기준 해석
목표: "실제 분해 실패에서 배운 해결 절차를 SKILL.md로 저장하고, 다음에 같은 조립체나 다른 조립체를 분해할 때 그 경험으로 더 잘하는 planner".

- **같은 조립체 — 지지됨 (이번 범위 안에서).**
  - 1차 시도 기록으로 만든 노트 SKILL.md를 쓴 B·C는, 2차 시도에서 기억 없는 A와 노트 없는 B·C보다 검사와 시간을 크게 줄였습니다(검사 3~10배 감소).
  - 05902에서는 1차 실패가 2차 성공으로 바뀌었습니다.
  - 한계: CAD 2개, 조건당 1~2회입니다. 05902 노트의 성공 순서는 A의 1차 성공에서 나왔습니다. 즉 "누군가 한 번 성공한 경험을 기억해 재사용"한 것입니다. 1차에서 아무도 성공하지 못한 조립체(05902의 B·C만 있었던 경우)에서 노트가 얼마나 돕는지는 이번에 시험하지 않았습니다.
- **다른 조립체 (일반 SKILL.md S3/S4b) — 혼재.**
  - 도움이 된 경우: 06146, 검증 05459(C+S4b가 검사 16회 vs A 46~177회).
  - 해가 된 경우: 05902.
  - 일반 문서는 그 가정(분해 축이 위쪽 등)이 맞는 조립체에서만 이득이었습니다. 가정을 먼저 확인하는 절차가 없고, 방향이 라벨 이름으로 해석되는 문제가 있었습니다.
- **구조 차이 (B vs C).**
  - C는 노트의 순서를 순위로 받아 호스트 DFS가 실행하므로 노트가 묻히지 않았습니다(S4b와 섞여도 성공).
  - B는 생성 코드가 일반 문서의 코드 틀을 따르다가 노트를 무시한 사례가 1건 있었습니다.
  - 반대로 C는 계약 위반으로 즉시 종료된 사례가 1건 있었습니다.

## 다음 개선 후보 (개발 데이터로만 만들고 새 CAD로 평가해야 함)
1. **축 확인 절차:** 일반 SKILL.md에서 고정된 "위 먼저" 대신, 처음 몇 부품에서 위·옆·아래를 한 번씩 시험하고 성공한 계열로 좁힙니다. 방향은 `direction_vectors_world` 기준으로 쓰고 라벨 이름은 쓰지 않습니다.
2. **노트 우선 규칙:** 정확히 같은 조립체의 노트가 있으면 그 성공 순서를 먼저 시도하도록 계약에 명시합니다(B 코드 틀 충돌 방지).
3. **계약 위반 복구:** 형식·계약 위반을 즉시 종료하지 않고, 호출 예산 안에서 한 번 다시 요청합니다(모든 조건 동일).
4. **provider 도구 차단 확대:** MCP 리소스 도구까지 끄는 설정을 찾거나, 도구 사용 거부 시 같은 호출을 한 번 다시 요청합니다(모든 조건 동일).
5. **물리 검사 속도:** 판정은 바꾸지 않고 속도만 올립니다. 05902의 거절 검사는 경로 샘플 2개에서 끝나는데도 2~3초가 걸립니다. 같은 900초 안의 성능에 직접 영향을 줍니다.
